## 1. Executive Summary & Root Cause Verdict

An exhaustive, evidence-based forensic investigation was conducted across the backend source code, Git deployment commit history, and the live production MongoDB Atlas database (`collegeservices_db`) to determine why assigned Seminar Hall Coordinators—specifically the Vice Principal (`viceprincipal`), assigned to Seminar Hall 4 (`SH-4`), as well as other hall coordinators—have received **zero** coordinator-specific seminar booking notifications and emails.

### The Explicit Forensic Verdict

The root cause of non-delivery to Seminar Coordinators is **NOT**:
1. ❌ **Coordinator Mapping**: The database mappings in `seminar_halls` (`coordinatorUserIds`) and `users` (`assignedHallIds`) are 100% correct, bidirectional, and active.
2. ❌ **Recipient Resolution in EmailService**: `EmailService.resolvePrimaryRecipients()` correctly resolves `SEMINAR_COORDINATOR` by specific `userId` and retrieves the user's registered email address.
3. ❌ **Email Provider Dispatch**: The Google Apps Script relay (`AppsScriptEmailTransport`) is fully operational (138+ emails delivered with HTTP 200).
4. ❌ **Spam Filtering / Network Delivery**: No emails were dropped in transit or rejected by SMTP.

The primary breakdown is **A SILENT IN-MEMORY NOTIFICATION GENERATION DEFECT**:
> **ROOT CAUSE 1 (CRITICAL CODE BUG):**  
> In `SeminarService.java`, the approval (`approveBooking`, line 1418), rejection (`rejectBooking`, line 1522), and cancellation (`cancelBookingDirectly`, line 1711) methods attempt to load the seminar hall using Spring Data's default repository method:  
> `SeminarHall hall = hallRepository.findById(booking.getHallId()).orElse(null);`  
> In MongoDB Atlas, the document primary key (`_id`) is an autogenerated BSON `ObjectId` (e.g., `ObjectId("6ab3eeae344f5a1ef4f8ef9a")`), whereas `booking.getHallId()` stores the string business identifier (e.g., `"SH-4"`, `"SH-3"`, `"SH-1"`).  
> Spring Data queries `{ "_id": "SH-4" }`, which returns **0 documents** (`null`).  
> Consequently, `if (hall != null)` evaluates to `false`, and the loop `for (String coordUserId : getCoordinatorUserIdsForHall(hall))` is **SILENTLY SKIPPED** on every booking approval, rejection, and cancellation across all halls!

> **ROOT CAUSE 2 (DEPLOYMENT TIMELINE MISMATCH ON CREATION):**  
> Coordinator notifications on booking creation (`createBooking`, lines 1042–1054) were only committed and deployed on **Nov 21, 2026 at 18:10:30 +0530** (Commit `e91d164`). Prior to that commit, coordinator notifications were governed by a legacy loop that checked `hall.getCoordinatorUserIds()`.  
> All 14 seminar bookings in MongoDB Atlas were submitted between **Nov 2, 2026 and Nov 21, 2026 11:34 AM**—**BEFORE** commit `e91d164` was deployed. Zero new seminar bookings have been created in the database since commit `e91d164` went live.

> **ROOT CAUSE 3 (EMPTY CC EMAILS CONFIGURATION):**  
> All 6 seminar hall documents in MongoDB Atlas have empty `ccEmails: []` arrays. While secondary to the primary coordinator routing, any CC-based email delivery for halls is currently unconfigured in the database.

#### Phase A: Booking Creation Execution
- When `AO-SEM-0025`, `AO-SEM-0034`, and `AO-SEM-0035` were created (Nov 20 and Nov 21 morning), commit `e91d164` had not yet been deployed.
- Even if it had been deployed, let us trace what occurred upon approval:

#### Phase B: Booking Approval Execution (`approveBooking`)
When AO Admin approved these bookings, the backend entered `SeminarService.approveBooking(String bookingId, User approver, ...)`:
1. **Line 1410–1415:** The requester notification was successfully created and dispatched:
   ```java
   notificationService.sendNotification(
       booking.getUserId(),
       "Seminar Request Approved (" + saved.getBookingId() + ")",
       ...
   );
   ```
   *(This generated in-app notifications and email logs for `ao`).*
2. **Line 1418:** The coordinator lookup executed:
   ```java
   // Line 1418 of SeminarService.java
   SeminarHall hall = hallRepository.findById(booking.getHallId()).orElse(null);
   ```
   - `booking.getHallId()` evaluated to `"SH-4"`.
   - `hallRepository` is a `MongoRepository<SeminarHall, String>`.
   - In Spring Data MongoDB, `findById(id)` translates to a query on the document identifier:
     $$\text{Query: } \{ \text{"\_id"}: \text{"SH-4"} \}$$
   - In MongoDB Atlas, the document for `SH-4` has:
     $$\text{"\_id"}: \text{ObjectId("6ab3eeae344f5a1ef4f8ef9a")}, \quad \text{"hallId"}: \text{"SH-4"}$$
   - Result of `findById("SH-4")`: **`Optional.empty()`**.
   - `hall` became **`null`**.
3. **Line 1419–1432:**
   ```java
   if (hall != null) {
       for (String coordUserId : getCoordinatorUserIdsForHall(hall)) {
           notificationService.sendNotification(
               "SEMINAR_COORDINATOR",
               "ADMIN",
               coordUserId,
               "Seminar Booking Confirmed",
               ...
           );
       }
   }
   ```
   - Because `hall == null`, `if (hall != null)` evaluated to **`false`**.
   - **The entire block was skipped!**
   - `notificationService.sendNotification(...)` was **NEVER INVOKED** for `viceprincipal`.
4. **Subsequent Handlers:**
   - Line 1435: `notifyAssignedTechniciansOnApproval(saved)` ran.
   - Line 1438: `notifyGeneratorOperatorsOnApproval(saved)` ran.
   - Line 1441: `notifyElectriciansOnApproval(saved)` ran.
   - `viceprincipal` was completely bypassed.

**Conclusion for `viceprincipal`:**  
No notification record was ever written to the `notifications` collection. Because no notification was written, `NotificationService` never triggered `EmailService.sendEmailForNotification(...)`. The email engine was never instructed to send an email to Dr. D. Suneel.
